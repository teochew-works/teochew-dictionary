# ADR-0021: One Drag Engine, Keyboard Parity, and Undo Instead of Confirmation

## Status

✅ Accepted

## Context

The flashcards screen (issues #187/#189/#192) is built around direct manipulation: decks live in a
library rail and are **dragged onto "the table"** to enter a session; a card can be filed into a
deck by dragging; a deck's contents open in a dock where rows can be reordered or moved between
decks; and a drag onto the trash deletes.

That is four superficially different drags — a deck out of the rail, a chip around the table, the
showing card into a deck, an entry out of the browse drawer. Implemented separately they would
drift: four hit-test implementations, four sets of feedback, four sets of edge cases, and no
consistent answer to "what will this drop actually do?"

Direct manipulation also raises two accessibility and safety questions. A drag-only interface is
unusable without a pointer. And destructive drops — deleting a deck, removing a card — invite a
confirmation dialog, which is the conventional answer and a bad one for an action a user performs
dozens of times in a session.

## Decision

**One drag engine, not four.**
[web/src/decks/dnd/useDeckDrag.ts](../../web/src/decks/dnd/useDeckDrag.ts) resolves every drag
against the same set of zones on every pointer move, via a pure, rect-based
[resolveDrop.ts](../../web/src/decks/dnd/resolveDrop.ts).

Three things follow from having a single resolution:

- **The drag image carries a badge naming the outcome** — `+18 cards`, `Already in Travel`,
  `Delete deck` — and turns red the moment a target refuses. The user reads the result before
  committing to it, which is only possible because one resolver already computed it.
- **Every drag has a keyboard equivalent**
  ([useDeckLift.ts](../../web/src/decks/dnd/useDeckLift.ts),
  [useCardLift.ts](../../web/src/decks/dnd/useCardLift.ts)): space lifts, arrows move — including
  between the rail and the table — space drops, escape cancels. Every outcome is announced through
  one aria-live region. Parity is achievable because both paths call the same resolver.
- **Modifiers and drop position ride the same machinery.** Holding the platform's copy modifier
  (Option on macOS, Control elsewhere —
  [copyModifier.ts](../../web/src/decks/dnd/copyModifier.ts)) turns a move into a copy, and the
  badge flips while the key is held. A deck's card list is itself a drop zone that can say *where*
  a card would land, so dragging within it reorders and dragging in files at a position.

**Destructive actions apply immediately and offer Undo in a toast**, rather than asking for
confirmation first — so the screen needs no modal dialog at all
([useToasts.ts](../../web/src/flashcards/useToasts.ts), with the undoable store actions in
[decks/actions.ts](../../web/src/decks/actions.ts)).

Where drag is not the right idiom at all, a pointer- and keyboard-native equivalent exists rather
than a modifier trick: `EntryDeckMenu` lists every deck as a checkbox, so ticking files and
unticking removes — and ticking a second deck without unticking the first is the copy that a
modifier-less path could not otherwise express.

Drag updates are kept **off the React render path** for pointer-rate work.

## Consequences

- Behaviour is consistent across every drag by construction, and a new drag source or drop target is
  a zone registration rather than a new implementation.
- **The interface is fully keyboard-operable and screen-reader-announced**, which a drag-only
  implementation would not have been. Parity is cheap here only because it was designed in from the
  single resolver rather than retrofitted.
- Undo-over-confirm removes every modal from the screen and makes the common case — filing and
  refiling cards quickly — fast, while still being recoverable.
- Negative: a real amount of custom code (a dnd directory of a dozen modules: geometry, physics,
  FLIP animation, reduced-motion, copy modifier, two lift hooks) in place of a drag-and-drop
  library. Justified by the badge-naming-the-outcome requirement, which needs the resolver to be
  the app's own, and by ADR-0019's minimal-dependency stance.
- Negative: undo has a window. An action undone after the toast expires has to be redone by hand.
- Negative: pointer-rate updates bypassing React means the drag path has its own state discipline,
  separate from the rest of the app's.
