# ADR-0014: Host Audio Bytes on GitHub Releases with an In-Repo Manifest

## Status

✅ Accepted

## Context

A pronunciation dictionary wants recordings. This is the repository's **first binary-asset
decision** — there are zero binary assets anywhere in `data/` today, and `dist/` is gitignored
build output rather than a committed precedent.

Three options were on the table (issue #32, [REVIEW.md § 12](../../data/phonology/REVIEW.md)):

- **Plain git.** Every clone grows forever as clips are added or re-recorded, and binary diffs are
  opaque. Re-recording a clip is a permanent addition to history.
- **Git LFS.** Keeps a clone shallow, but adds a real dependency nothing else here needs: LFS
  quota and bandwidth, plus every contributor installing `git-lfs`.
- **External object storage plus a committed manifest.**

Scale, from § 10/§ 11: 340 (syllable, variety) pairs attested at the time, with a low-thousands
ceiling once tone-sandhi surface forms are included (§ 14 confirms they are). Each clip is a short
single-syllable recording — plausibly tens of KB as opus.

## Decision

*Amended 2026-09-07 (issue #228):* every clip's `url` may now carry an optional CAF/Opus sibling,
`cafUrl`, for iOS-native playback — AVFoundation has no WebM demuxer at all, confirmed by direct
testing, so the ~98% of the corpus recorded as WebM/Opus could not play in the native app at all.
CAF over some other iOS-compatible container (e.g. re-encoding to AAC/M4A) because it has supported
Opus specifically since iOS 11: `afconvert` has no lossless remux path either way (it always
decodes+re-encodes, even Opus-to-Opus), but keeping the same codec and matching the re-encode's
bitrate to the source avoids *also* changing codec, which would compound the quality loss of that
unavoidable second lossy pass. Nothing below about *how* a clip's bytes are hosted changed — this
only adds a second, optional asset per clip and the release-placement convention it needs; see the
new schema bullet and convention paragraph below, and the confirmed release cap in Consequences.

*Amended 2026-09-07 (issue #237):* this record covers where clip bytes are *stored*. How they are
*served* — the read path, its cache and CORS behaviour, and whether it survives a large audience —
is [ADR-0026](adr-0026.md), which also names the trigger for moving off Release hosting and the
migration that follows.

**External object storage, not git.** Clip bytes are hosted as **GitHub Release assets**; only a
YAML manifest is committed to [data/phonology/audio/](../../data/phonology/audio/). Clip bytes never
enter this repo's git history, and no LFS store is used.

GitHub Releases specifically, because it needs **zero new infrastructure**: it reuses the repo's
existing hosting, assets are versioned by release tag, it is free at this scale, and an upload is
human-browsable for spot-checking. A cloud bucket (S3/R2/GCS) would need an account, credentials
and a billing relationship this project does not otherwise have.

How the schema embodies it (`audioClip` in
[packages/core/src/schema/phonology.ts](../../packages/core/src/schema/phonology.ts)):

- **`url`** is a full, regex-constrained GitHub Release asset download URL,
  `.../releases/download/<tag>/<asset>` — deliberately **not** the floating
  `/releases/latest/download/...` alias, because a stored reference must be pinned to a tag so it
  cannot silently start pointing at different bytes. A full URL is stored per clip, rather than a
  bare filename plus a reconstructed base-URL convention: it is self-describing, and it lets one
  variety's hosting move independently of another's. *Amended 2026-09-07 (issue #237): that last
  clause is true of the data shape but not of the schema as it stands* — `GITHUB_RELEASE_ASSET_URL`
  pins every URL to this repo's own `releases/download/` path, so no other host validates today.
  Widening it is step one of ADR-0026's migration, and costs a core version bump.
- **`checksum`** is **required**, not optional. With no git-tracked local copy, it is the only
  integrity check available.
- **`sources`** derives `licence` unchanged (ADR-0015).
- **`cafUrl`/`cafChecksum`** *(added 2026-09-07, issue #228)*: an optional CAF/Opus alternate for
  `url`'s WebM/Opus bytes, same URL shape and integrity rule as `url`/`checksum`. Paired — a schema
  refine rejects either field without the other — so a CAF reference can never exist without its
  own checksum. Absent for a clip that needs no alternate (e.g. an already-`.wav` clip); a consumer
  that wants iOS playback falls back to `url` when it's undefined.

Convention, non-binding: one release per variety (tag `audio-chaozhou`), assets uploaded into the
existing release rather than a new tag per batch, filenames plain ASCII and hyphenated to avoid
percent-encoding noise in stored URLs — which is why rehosting strips diacritics from asset names.

*Added 2026-09-07 (issue #228):* a `cafUrl` asset is deliberately **not** uploaded into its source
clip's own release — see the confirmed release cap below, which several of the existing per-variety
`.webm` releases were already at or near. Instead, CAF assets for a variety go into a release
dedicated to the format, `audio-<variety>-caf`, rolling over to `-caf-2`, `-caf-3`, ... as that cap
is met — one release-per-variety-per-format, rather than one release-per-variety. Asset filenames
are prefixed with the source clip's own release tag (e.g. `audio-teochew-dictionary-audio-4-du2.caf`)
to stay unique now that one release can hold CAF siblings whose sources span several different
`.webm` releases. See `backfillCafOpus` in
[src/importers/caf-backfill.ts](../../src/importers/caf-backfill.ts) (driven by
`npm run backfill:caf-opus`, dry-run by default) for the mechanics, and
[src/importers/caf-encode.ts](../../src/importers/caf-encode.ts) for the `ffmpeg`/`afconvert`
transcode itself.

## Consequences

- **Every git-tracked file in `data/` stays plain text and diffable, audio included** — the direct
  extension of ADR-0005 to binary content. A reviewer sees a URL, a checksum and a licence, all
  reviewable in a normal diff.
- Clones stay small no matter how much audio accumulates, and a re-recording replaces an asset
  rather than adding to history forever.
- **Accepted trade-off: the dataset is no longer self-contained.** A consumer needs network access
  to actually hear a clip, and someone has to own hosting long-term.
- Negative: integrity now depends on `checksum` plus a command nobody runs automatically
  (ADR-0012). A silently replaced asset would go undetected until someone runs `npm run audio:verify`.
  *Amended 2026-09-07 (issue #237):* that command verified only `url`/`checksum` until issue #238,
  leaving every CAF alternate — half the published assets — unchecked while still reporting success.
  It now fetches both, which roughly doubles its runtime.
- **Accepted trade-off: publishing is one network round-trip per clip, and there is no batch.**
  The Releases API has no primitive for uploading several assets in one call, so every tool that
  publishes a clip (`rehostClip`, `mergeLocalRecording`, `backfillCafOpus`) does one
  `gh release upload` per clip. Measured during the issue #228 backfill, a clip costs ~2.5s all-in:
  ~0.7s to fetch the source, ~1.7s to upload, and a negligible ~0.06s to transcode — so a run over
  N clips costs about `N × 2.5s`, and the 3,086-clip Chaozhou backfill took roughly two hours. The
  existence check that used to add ~1.2s per clip is cached per tag since issue #233.
- Negative: that cost is I/O wait, which would parallelise, but three things currently prevent it —
  every external call in `caf-encode.ts` and `lingualibre-rehost.ts` uses blocking `execFileSync`;
  `createCafTagAllocator` tracks its asset count in-process with no synchronisation; and
  `backfillCafOpus` deliberately rewrites the whole manifest after each clip so an interruption
  cannot lose committed progress, which is safe for one writer and unsafe for several (issue #243).
- Negative, recorded as a caveat rather than a claim: no documented cap on assets-per-release or
  total Releases storage was confirmed. Assessed low risk at these file sizes; splitting across
  releases is the trivial mitigation, and per-variety releases already do so.
  *Confirmed 2026-09-07 (issue #228): GitHub caps a release at exactly 1000 assets* — hit for real
  partway through backfilling CAF alternates onto the Chaozhou corpus (a real `gh release upload`
  returned `HTTP 422: file_count limited to 1000 assets per release`). The anticipated mitigation
  was correct: a release hitting the cap rolls over to a new numbered one
  (`audio-<variety>-caf-2`, `-caf-3`, ...), same as several `.webm` releases already had to before
  this was ever confirmed.
  *Amended 2026-09-07 (issue #237): that cap is consumed by superseded assets too.* Comparing each
  release's asset list against the URLs the manifest actually references, 718 of the first `.webm`
  release's 1000 slots hold re-recorded clips whose filenames are now referenced under a later tag —
  it sits at the cap with 28% of it live. Splitting across releases remains the trivial mitigation,
  but some of the splitting done so far bought capacity that reclaiming stranded assets would have
  bought instead (issue #241).
