# ADR-0000: Use Architecture Decision Records

## Status

✅ Accepted

## Context

This project has accumulated an unusually large body of recorded rationale for its size: the
decision to store only Peng'im and derive everything else, the licence-derivation rules, the
importer staging boundary, the audio hosting and consent model, and a series of approaches that
were considered and rejected.

That rationale is recorded **informally**, spread across four places:

- [README.md](../../README.md) — 1000 lines, organised by issue number, mixing "how to run the
  command" with "why the command is shaped this way".
- [data/phonology/REVIEW.md](../../data/phonology/REVIEW.md) — seventeen numbered sections, several
  of which open with an explicit **Decision:** paragraph (§ 12 audio hosting, § 13 licensing and
  consent, § 17 recording from the browser) alongside genuinely open linguistic questions.
- [web/README.md](../../web/README.md) — an *Architecture* section carrying the frontend's
  decisions.
- Long explanatory comments in source, e.g. `BASE_LICENCE` in
  [src/data/licence.ts](../../src/data/licence.ts) and `IMPORTER_USER_AGENT` in
  [src/importers/types.ts](../../src/importers/types.ts).

That record is valuable and should stay where it is — it is what a contributor reads while doing
the task. But it is not a versioned, status-tracked decision corpus. There are no stable
identifiers to cite, no status lifecycle (proposed → accepted → superseded), no explicit
supersession links, and a decision is discoverable only by reading the how-to section it happens
to live inside. Decisions also get *unwritten* by editing: when issue #53's Mandarin-frequency
approach was superseded by issue #54's `insource:` search, what survives in the README is a
two-word parenthetical.

We need a lightweight, version-controlled method for recording significant decisions — including
the decisions to *not* pursue an approach, which are some of the most valuable history here.

## Decision

We will use Architecture Decision Records (ADRs) to document significant architectural, data-model,
licensing, and product decisions for the Teochew Dictionary.

Each ADR follows the format popularized by Michael Nygard:

- **Title** — a short noun phrase describing the decision (e.g., "ADR-0001: Store Peng'im Only;
  Derive IPA, POJ and Sandhi"). A decision to reject an approach is phrased as "Reject X".
- **Status** — one of `Proposed`, `Accepted`, `Deprecated`, or `Superseded`, shown with the emoji
  from the [inventory legend](README.md#status-legend). A decision to reject an approach is
  `Accepted` — the decision *to reject* is what is in effect.
- **Context** — the forces at play (technical, linguistic, legal, project-specific).
- **Decision** — the response, stated in active voice ("We will ..." / "We will not ...").
- **Consequences** — the resulting context: positive, negative, and neutral outcomes.

ADRs will be:

- Stored in `docs/adrs/` within the repository, versioned alongside the code and data they describe.
- Written in Markdown, with the `# ADR-NNNN: Title` heading as the **first line** of the file and
  no YAML front-matter, so the `update-adr-inventory` tooling can parse them reliably.
- Numbered sequentially with zero-padded four-digit identifiers (`adr-0001.md`, `adr-0002.md`).
  Numbers are never reused; superseded ADRs remain in the repository for historical reference.
- Kept concise — ideally one to two pages.
- Scoped to a single decision per record.
- When citing source code or data, use file paths and stable symbol names (functions, exported
  constants, schema fields, YAML keys) only — never specific line numbers. Line numbers drift the
  moment any unrelated commit shifts lines above the cited range, even when the cited content
  itself is untouched.

The inventory table in [README.md](README.md) is regenerated by the `update-adr-inventory` skill,
which reads each ADR's title and status and derives the date from git. The `review-adr` skill
checks new and existing ADRs against this format.

ADR-0001 through ADR-0022 are **retrospective**: they were written in one pass over the project's
existing record, so their git-derived dates are all the date of adoption rather than the date each
decision was made. Each record states its own decision date and issue number in the text.

## Consequences

- Every significant decision — including rejected approaches like TTS synthesis and the HSK 3.0
  crosswalk — has a stable, citable ID and a written record.
- ADRs complement the existing documentation rather than replacing it: `README.md` and
  `web/README.md` explain *how to use the project today*, `data/phonology/REVIEW.md` tracks *open
  linguistic questions*, and the ADRs record *why we chose what we chose and what we rejected*.
  Where a decision has a fuller narrative in one of those documents, the ADR links to it rather
  than duplicating it.
- Superseded decisions stay in the repository, preserving how the design evolved.
- There is a small overhead in writing and maintaining ADRs, offset by less repeated discussion
  and faster onboarding — this project takes contributions from people who know Teochew but not
  the codebase, and from people who know the codebase but not Teochew.
- The retrospective batch carries a known limitation: it reconstructs rationale from what was
  written down at the time, so a decision made without a written trace is not in the corpus.
