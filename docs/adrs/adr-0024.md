# ADR-0024: Shared Logic Lives in `@teochew/core`, Published from This Repo

## Status

✅ Accepted

## Context

Builds on [ADR-0019](adr-0019.md) (`web/` is an independent npm project) and
[ADR-0020](adr-0020.md) (the hand-rolled SM-2 scheduler). Amends [ADR-0004](adr-0004.md), whose
"schemas live in `src/schema/`" is now only half true.

[ADR-0023](adr-0023.md) rejected a native rewrite of the web app because it "doubles the maintenance
surface for a project with one shared implementation of the dictionary, SRS scheduler, and
drag-and-drop UI." A separate project — [teochew-dictionary-app](https://github.com/teochew-works/teochew-dictionary-app)
— then chose React Native anyway, for reasons that are its own (local-and-cloud user data, a
framework that can grow past what a PWA can do; see that repo's ADR-0001). That left exactly the
problem ADR-0023 warned about: a second implementation of the phonology derivation, the SM-2
maths, and the deck/search pipeline, free to drift from the first without anyone noticing.

Most of that logic was already pure TypeScript with no DOM, filesystem, or React dependency, and
already unit-tested: `src/schema/` and the derivation half of `src/phonology/` at the repo root;
`srs/scheduler.ts`, `decks/pipeline.ts`, `search/filters.ts`, `search/sortEntries.ts` and the
flashcard filter predicates in `web/src/`. Only the *edges* — reading YAML from disk, IndexedDB,
React hooks — were platform-specific.

The two projects are separate git repositories, deliberately. ADR-0019 keeps `web/` out of the
root `package.json` so a frontend dependency bump never touches the CLI tooling's tree; folding a
React Native app in as well would cut against that harder still.

The decision was made in the app repo (its
[ADR-0002](https://github.com/teochew-works/teochew-dictionary-app/blob/main/docs/adrs/adr-0002.md),
2026-09-02) and implemented here. This record exists because the consequences land on *this*
repo's contributors — where a schema change goes, what a scheduler fix has to go through before
mobile sees it — and until now nothing in this repo's own guidance said so.

## Decision

We will keep the DOM-, filesystem- and React-independent logic in one package,
[`packages/core/`](../../packages/core/README.md), published as **`@teochew/core`** from this
repo and consumed as an ordinary npm dependency by `web/` here and by `mobile/` in the app repo.

**What belongs in core.** Anything that is a pure function of its arguments and that both
apps need to agree on: the entry and phonology Zod schemas; Peng'im syllable parsing and
IPA/POJ/sandhi derivation given the phonology tables as parameters; the SM-2 scheduler; the deck
pipeline and card filter/sort logic; the flashcard-eligibility predicates; text normalisation —
and every one of their test suites.

**What does not.** Anything that reads a file, opens a database, or renders. Loading the
phonology tables from `data/` stays in the root project's `src/phonology/load.ts`; the root
`src/phonology/*.ts` files are thin wrappers that load from disk and delegate to core, keeping
their original signatures. IndexedDB (`web/src/srs/db.ts`, `web/src/decks/storage.ts`), SQLite,
and React hooks/components stay in the app that owns them. Persistence and rendering are exactly
where the platforms differ, so they are exactly what core must not contain.

**The rule for contributors.** A change to shared logic is made in `packages/core/`, once, with
its tests — never by patching the wrapper in `src/`, never by adding a local copy in `web/src/`.
If a fix seems to need to live in a consumer, the consumer is missing an adapter boundary, not
core a special case.

**Versioning.** Core carries its own `version` in `packages/core/package.json` and follows
semver. While the major version is `0`: a bug fix or a purely additive export bumps the patch; any
change to an exported signature, exported type, or observable behaviour a consumer could depend
on bumps the minor and is called out in the commit. `web/` consumes core via a `file:` link and
therefore always tracks the working tree; `mobile/` pins a version, so **it is normal for the two
consumers to be on different versions**, and a change to core is not "done" for mobile until the
release below has been cut and the app repo has bumped its pin.

**Releasing.** Publishing is a deliberate maintainer action, never something CI does on push —
the same stance as `.github/workflows/release-dict-sqlite.yml` and the audio release assets
([ADR-0014](adr-0014.md)), and for the same reason: a public release asset is a visible action
someone should have chosen to take. Until `@teochew/core` is on the npm registry, the release path is
`.github/workflows/release-core-tarball.yml`: bump `version`, merge, dispatch the workflow, which
runs core's `check`, `npm pack`s, and attaches the tarball to an immutable `core-tarball-v<version>`
GitHub Release. The registry path (`publish-core.yml`, on a `core-v*` tag) exists but is inert
until an `NPM_TOKEN` secret is added; the tag prefixes differ so that cutting a tarball can never
accidentally attempt a registry publish.

**A known impurity, to be removed.** `flashcards/promptMode.ts`, `flashcards/levelFilter.ts` and
`settings/pronunciationMode.ts` in core still export `localStorage`-backed `read*`/`write*`
helpers, because the extraction moved those files whole. They violate the boundary above.
Consumers must use only the pure types and predicates from those modules; the helpers will move
back into `web/` in a minor bump rather than be relied on.

## Consequences

- A phonology fix, a scheduler fix, or a deck-filtering rule change is written and tested once and
  reaches both apps — the drift ADR-0023 was worried about cannot happen silently, only by a
  consumer failing to bump.
- Every contributor to this repo now has a third project to know about. Root `npm ci` builds
  core's `dist/` automatically (the `file:` dependency's `prepare` script), but **after editing
  `packages/core/src/`, `npm run build` in `packages/core` is required before the root or `web/`
  `check` sees the change** — both import `dist/`, which is gitignored. CI runs core's own `check`
  as a separate job, so a broken core fails visibly even if a consumer's tests happen to pass
  against a stale build.
- Shared logic now has a public API surface with two consumers. Renaming an export is a
  cross-repo change, and the cost of "just tidying" core is correspondingly higher than it was
  when the same code was private to `web/`.
- The root project's `src/schema/` and `src/phonology/` directories no longer hold what their
  names and ADR-0004 suggest; the wrappers that remain exist for the root tooling's convenience
  and are not the place to change anything.
- A cross-repo release step exists that did not before. It is manual and version-pinned on the
  mobile side by design, which means a change can be merged here and still be absent from the
  app for as long as nobody cuts a release — an explicit "bump the pin" step in the app repo is
  part of finishing any core change mobile needs.

## Alternatives considered

- **Merge the two repos into one monorepo** (workspaces, no publishing). Rejected: contradicts
  ADR-0019's separation of the tooling and frontend trees, and would add a React Native toolchain
  to the checkout of everyone who only wants to edit YAML.
- **Git submodule of this repo inside the app repo.** Rejected: pins by commit rather than by
  version, gives the consumer the whole tooling tree to get a few source files, and submodules'
  update ergonomics are a well-known contributor trap.
- **Reimplement the logic natively in the app.** Rejected — this is the drift scenario the
  package exists to prevent; the app repo's own ADR-0002 rejects it at length.
- **Copy the files across and diff periodically.** Rejected for the same reason, with worse
  tooling.
- **Publish straight to npm from the start** instead of a tarball stopgap. Deferred, not
  rejected: the registry workflow is in place, but claiming the `@teochew` scope and committing to
  a public package is a maintainer decision with an audience beyond these two repos.
