# ADR-0001: Responsive PWA instead of a native wrapper, and Workbox as an exception to hand-rolling

## Status

Accepted

## Context

Issue #194 asked whether the app needed real mobile support, and if so, what form it
should take. The investigation is [docs/design/mobile.md](../design/mobile.md); this ADR
records only the decision that came out of it and the one implementation choice inside
that decision (Workbox) that departs from an established project convention.

The app's own audit found nothing that needs a native capability. Storage is IndexedDB
plus localStorage; audio playback is a plain `<audio>` element against remote URLs; the
one path that touches a native-feeling API (`RecordClipButton`'s `MediaRecorder` control)
is gated behind `import.meta.env.DEV` and never ships to production (issue #128,
`data/phonology/REVIEW.md` § 17). A Capacitor- or Cordova-style shell would wrap the same
web view around the same code, adding a build target, a signing story, a review cycle, and
recurring developer-account cost — for a website that would just be a website inside a
wrapper, which Apple's App Store guideline 4.2 explicitly disfavors.

The one plausible future driver for going native — push notifications for review reminders
— doesn't require it either: iOS has supported Web Push since 16.4 for home-screen-installed
web apps.

The strongest actual argument for installing at all isn't offline access — it's storage
durability. Safari's Intelligent Tracking Prevention deletes all script-writable storage
(the IndexedDB store holding SRS review history, and the localStorage holding decks) after
7 days without a visit; a home-screen-installed web app is exempt from that sweep. For an
app whose entire value is accumulated review history, that eviction is the difference
between a tool and a toy.

## Decision

Ship the app as a responsive web app, installable as a PWA (manifest, icons, a service
worker that precaches the shell). No native wrapper, now or as a near-term default.

The service worker is generated by `vite-plugin-pwa` in its `generateSW` (Workbox) mode,
rather than hand-written. This is a deliberate exception to a preference stated repeatedly
in this codebase's own comments — `srs/scheduler.ts`'s "deliberately dependency-free...
matching the rest of the repo," echoed by `decks/dnd/useDeckDrag.ts`'s "matching this
repo's preference for small hand-written implementations." Two reasons it doesn't apply
here: the precache manifest has to be generated from hashed build output (there's no small
hand-written version of "know every current asset's cache-busted filename"), and hand-rolled
cache invalidation for a service worker is a well-known way to brick a static site —
getting it wrong doesn't degrade gracefully, it stops the app loading at all for anyone
already holding a stale worker.

Everything else about the PWA setup stays deliberately narrow, to keep as much of the
"small, understood implementation" preference as the exception allows:

- The precache list is restricted to the shell (`globPatterns` limited to
  `js/css/html/png/svg/ico`, plus an explicit `globIgnores` for `data/**` as a second
  layer) — never `dict.json` (41MB decoded). Making that available offline is a separate,
  explicit opt-in (`src/pwa/offlineData.ts`), handled by hand directly through the Cache
  Storage API rather than through Workbox at all, for the same small-and-legible reason
  this ADR otherwise defers to Workbox: whether dict.json is cached is a decision a person
  made on Settings, not an automatic route-matching side effect of visiting the page.
- `registerType: 'prompt'`, not the plugin's default silent `autoUpdate` — a background
  reload landing mid flashcard review would drop the session, so the update itself is
  still hand-decided even though the worker that ships it isn't hand-written.
- The manifest's `start_url`/`scope` reuse the same `base` value `vite.config.ts` already
  computes for GitHub Pages, rather than a second hardcoded path that could drift from it.

## Consequences

- One new dependency (and its Workbox transitive dependencies) where the project otherwise
  minimizes them. Scoped to build tooling — nothing at runtime depends on `vite-plugin-pwa`
  itself; the output is a plain generated `sw.js`.
- The precache manifest, and therefore what's available offline, is opaque to a reader who
  doesn't already know Workbox's `generateSW` conventions — a real cost against this
  project's stated preference for implementations a contributor can read start to finish.
- iOS still requires the manual "Share → Add to Home Screen" flow; there is no
  `beforeinstallprompt` there and no way to add one. Settings frames the install prompt as
  "keep your review history," not "work offline," since durability — not offline access —
  is the actual benefit on every platform.
- Revisiting this decision would matter if a genuinely native capability shows up as a hard
  requirement (background sync notifications beyond what Web Push covers, e.g.) — nothing
  audited for issue #194 currently needs one.

## Alternatives considered

- **Capacitor/Cordova native wrapper.** Rejected: no native capability is needed, and it
  adds a build target, signing, app-store review, and annual cost for what the App Store
  guidelines already flag as against the rules for a wrapped website.
- **Full native rewrite (Swift/Kotlin).** Rejected outright — doubles the maintenance
  surface for a project with one shared implementation of the dictionary, SRS scheduler,
  and drag-and-drop UI today, none of which would carry over.
- **Hand-rolled service worker**, keeping the no-new-dependency line intact everywhere.
  Rejected for the reason above: a hand-rolled cache-invalidation strategy for hashed build
  output is exactly the kind of small-looking implementation that is disproportionately
  easy to get wrong, and wrong here means the app stops loading rather than degrading.
