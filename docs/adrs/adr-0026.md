# ADR-0026: Serve Audio Direct from Release Assets Until a Named Trigger

## Status

✅ Accepted

## Context

[ADR-0014](adr-0014.md) decided where clip bytes are *stored*: one clip is one GitHub Release
asset, and the committed manifest holds a full, individually-fetchable URL per clip. It reasoned
about clones, LFS quota and integrity — all write-side concerns. It never reasoned about the read
path, and neither has anything since. This record covers serving.

The read path today is as direct as it gets. A clip's pinned URL is copied verbatim from
[data/phonology/audio/](../../data/phonology/audio/) into `dict.json` and `sounds.json` by
`resolveClipForKey` and `buildSounds`, shipped to the browser, and assigned to a bare
`HTMLAudioElement` by `useAudioPlayer` in
[web/src/hooks/useAudioPlayer.ts](../../web/src/hooks/useAudioPlayer.ts). Nothing rewrites the URL,
proxies it, caches it, or verifies it at play time. The corpus is 3,088 Chaozhou clips, each with a
CAF sibling (issue #228) — 6,176 assets across eight releases, about 132 MiB in total, averaging
~17 KB per WebM clip and ~22 KB per CAF.

Measured against a live asset on 2026-09-07, a clip fetch behaves like this:

- `github.com/<owner>/<repo>/releases/download/<tag>/<asset>` answers **302 with
  `cache-control: no-cache`**, redirecting to `objects.githubusercontent.com` (Azure Blob storage
  behind Fastly).
- The asset response carries **no `Cache-Control` at all** — only `etag` and `last-modified`.
- It carries **no CORS headers anywhere in the chain**, and arrives as
  `content-type: application/octet-stream` with `content-disposition: attachment`.

Three consequences fall straight out of those headers, and none of them are ours to change:

- **Every play costs two round-trips**, and the first is explicitly uncacheable, so `github.com`
  itself is contacted for every single clip a user hears.
- **Caching is heuristic, and inverted.** With no `Cache-Control`, browsers guess freshness from
  `last-modified` age — so a freshly recorded clip, the kind being actively listened to, gets close
  to no caching, while an old one gets months of it.
- **`fetch()` can only ever obtain an opaque response**, which rules out verifying a clip's
  `checksum` at play time, any service-worker retry, and storing clips in Cache Storage on terms
  worth having. That is why [docs/design/mobile.md](../design/mobile.md) rejects caching audio in
  v1, and why the opt-in offline data of [ADR-0023](adr-0023.md) covers `dict.json` alone.

The bandwidth question has no published answer to design against. GitHub's Releases documentation
states there is "no limit on the total size of a release, nor bandwidth usage." GitHub's Acceptable
Use Policies, under *Excessive Bandwidth Use*, reserve the right to "suspend your Account, throttle
your file hosting, or otherwise limit your activity" where bandwidth is "significantly excessive in
relation to other users of similar features." Those two statements are in tension, and the tension
is the whole finding: the ceiling here is discretionary, not documented.

Scale makes the shape concrete. Lifetime downloads across every audio release currently total
roughly **10,700** — four orders of magnitude below anything that would draw attention. At a
hypothetical million monthly users playing ~30 clips each, the same corpus serves ~510 GB and
~30 million redirect requests against `github.com` per month. The bytes are unremarkable; a
request pattern that unlike ordinary release downloads is what would invite the AUP clause.

## Decision

**We will keep serving clips directly from their pinned Release asset URLs, and will not
pre-emptively migrate.** At present traffic the current model costs nothing, runs no
infrastructure, and preserves [ADR-0019](adr-0019.md)'s "zero hosting cost and zero operational
burden". Migrating now would buy nothing and spend a billing relationship this project does not
have.

**We will migrate when one of these triggers fires.** Any throttling notice, abuse flag or
observably rate-limited asset request from GitHub is decisive on its own. Failing that, rolling
30-day asset downloads crossing roughly 10⁵ is the point to re-measure and re-read this record,
and roughly 10⁶ the point to begin migrating. Those two numbers are judgment calls stated plainly
as such — GitHub publishes no figure to anchor them to, and the honest position is a band, not a
threshold. Separately and regardless of volume, **deciding to ship offline audio or play-time
integrity checking is itself a trigger**: both need CORS, Release assets will never send it, and no
amount of remaining headroom changes that.

The trigger is only meaningful if someone can see it coming. Per-asset `download_count` from
`gh api` is the one piece of telemetry this model provides for free; issue #242 covers turning it
into a sampled rate, since the counter is cumulative and a single reading says nothing.

**When the trigger fires, the migration is mechanical**, and worth writing down now so the trigger
is actionable later:

1. Widen `GITHUB_RELEASE_ASSET_URL` in
   [packages/core/src/schema/phonology.ts](../../packages/core/src/schema/phonology.ts) to admit a
   second approved host. Because it lives in core, that means a version bump, a tarball release and
   a mobile pin update ([ADR-0024](adr-0024.md)).
2. Mirror the assets to a zero-egress object store behind a CDN, verifying the mirror against the
   `checksum` and `cafChecksum` already in the manifest.
3. Rewrite the manifest's URLs by byte-offset splice ([ADR-0018](adr-0018.md)), never
   parse→stringify.

One correction to ADR-0014 belongs here, because it is what makes step 1 necessary. That record
justifies storing a full URL per clip partly on the grounds that "it lets one variety's hosting
move independently of another's". That is true of the *data shape* and false of the *schema today*:
`GITHUB_RELEASE_ASSET_URL` pins every URL to this repo's own `releases/download/` path, so no
non-GitHub URL can validate. The escape hatch was designed, and is currently welded shut.

## Consequences

- **Negative: no offline audio, and no integrity check at play time**, for as long as this stands.
  Both trace to a single absent CORS header on a host we do not control. An installed PWA offline
  is dictionary text only.
- **Negative: `github.com` sits in the path of every play**, rather than a CDN edge, and the clips
  most likely to be played are the ones least likely to be cached.
- **Negative: the AUP exposure is discretionary and, until issue #242 lands, unmeasured.** The
  mitigating fact is the size of the gap: current traffic is four orders of magnitude below the
  range where the question becomes real.
- Negative: the client cannot tell a rate-limited clip from a finished one. `useAudioPlayer`'s
  `onerror` handler simply un-sticks the play button, so throttling would surface as clips silently
  not playing rather than as an error anyone could diagnose.
- **Positive: zero infrastructure, zero cost, no credentials and no billing relationship**, exactly
  as ADR-0014 and ADR-0019 intended.
- Positive: migration is mechanical rather than architectural, because the manifest already stores a
  self-describing URL *and* a checksum per clip. The data model survives a hosting change; only the
  schema's host constraint and the stored URL strings need to move.
- Neutral: bytes are not the constraint here and never were. The entire corpus is ~132 MiB. Request
  count, cache headers and CORS are what bind.

## Alternatives considered

- **Re-host under the GitHub Pages origin.** Suggested in `docs/design/mobile.md` as "the honest
  fix", and it genuinely solves the CORS and caching problems — same origin as the app, with headers
  the project controls. But Pages publishes a **1 GB site cap and a 100 GB/month soft bandwidth
  limit**, and states it "is not intended for or allowed to be used as a free web-hosting service".
  The 132 MiB corpus fits the size cap comfortably; the ~510 GB/month of the scale case exceeds the
  bandwidth limit fivefold. So it swaps an undocumented discretionary ceiling for a documented and
  *lower* one. Worth doing if offline audio becomes the priority at current traffic; not an answer
  to scaling.
- **Move to an object store behind a CDN now** (R2, S3, B2). The eventual destination, and the
  reason step 2 above is written the way it is. Rejected as premature for the same reason ADR-0014
  rejected it: it needs an account, credentials and a billing relationship the project does not
  otherwise have. Issue #206 on sustainable funding is the natural precondition.
- **Bundle clips into per-variety archives.** Would collapse request count dramatically, and at
  132 MiB the whole corpus is small enough to make per-variety bundles plausible for offline use.
  Rejected as the *primary* path because it breaks the property the whole model was built around —
  a consumer fetching one specific syllable on demand, without downloading and unpacking a bundle
  first. It stays a reasonable shape for an explicit offline download later.
- **Front the existing release assets with a public CDN** (e.g. jsDelivr, which does serve GitHub
  release assets and would add both CORS and real cache headers). Rejected because it makes the
  app's core function depend on a third party's free tier and abuse policy, trading GitHub's
  discretionary ceiling for another one with no more contractual footing — while adding a hop
  neither this project nor GitHub controls.
