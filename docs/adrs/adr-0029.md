# ADR-0029: Multiple Takes per Speaker: `take` and `primary` on Audio Clips

## Status

✅ Accepted

## Context

Issue #290 (2026-09-18). Issue #134 made a clip's slot in `clips[<pengim>]` be identified by its
`speaker`: a *distinct* speaker's clip appends cleanly, and `checkDuplicateSpeakers` in
[src/validate/index.ts](../../src/validate/index.ts) makes one-clip-per-speaker-per-key a hard
validation error. That convention has held for every clip merged since, and it is what lets
`clipsFor`/`selectReadingClips` find "the `jky` clip" by name.

Issue #288's elicitation UI (2026-09-18) broke the assumption underneath it. It deliberately lets a
contributor record *several takes* of the same target before a human picks one, and defers speaker
assignment to merge time — as of that date the branch holds 414 unassigned staged takes across 106
syllables, up to 8 for `ku3`. Staging already accommodates them (#135's one-proposal-per-key rule
was relaxed for a deferred-speaker save). Publishing them does not: `mergeLocalRecording` and
`mergeLinguaLibreClip` both locate the slot with `existingList.findIndex(c => c.speaker === speaker)`
and then either refuse, or, under `--force`, *replace* — overwriting the merged take in the YAML and
its S3 object both. A `data/staging/recordings/` take, once merged and cleaned up, is not
recoverable, and because [src/importers/s3-upload.ts](../../src/importers/s3-upload.ts) uploads with
`Cache-Control: immutable`, the clobbered object also needs a manual CloudFront invalidation before
the new bytes are served. So today one can publish exactly one take per speaker per syllable, or
lose one.

Underneath that, `speaker` is doing three jobs at once: *who recorded it*, *which tier it is*
(`jky` versus ADR-0027's `jky-n` render), and — if #288's second session were published as `jky-2` —
*which session it belongs to*. That overloading is what makes the model awkward to extend.

A survey of every consumer of `clips[]` (2026-09-18) found they want different things. UI playback
(`selectPrimaryClip` in [src/build/enrich.ts](../../src/build/enrich.ts), the Sounds tab, #274's
client-side speaker preference) wants exactly one clip per speaker per syllable, chosen by a human
and stable across builds. The held-out classifier eval that #288 exists to feed (#279, #280, #285)
wants a *set* of genuinely independent takes from one person, separable from the published one.
The ADR-0027 render tier and `audio:grade` both want one sample per syllable per speaker —
`src/audio/synthesize.ts` keys jobs by syllable, so two recordings at one key collide silently and
`derivedFrom` can name the wrong take, and a syllable with 8 takes would carry 8× weight in the
per-tone medians. Storage wants a distinct, immutable path per take. And a human hand-editing
`data/phonology/audio/chaozhou.yaml` wants a rule small enough to hold in their head, where every
mistake fails `npm run validate` instead of silently changing playback.

## Decision

We will keep `clips[<pengim>]` a flat list and let it hold more than one clip per speaker, so that
**`checksum` is the identity of a clip and `speaker` is the identity of a *person* only.** Two
optional fields on `audioClip`
([packages/core/src/schema/phonology.ts](../../packages/core/src/schema/phonology.ts)) carry the
rest:

```yaml
ku3:
  - { url: …/jky/ku3.webm,       speaker: jky, primary: true, … }   # existing entry + one new line
  - { url: …/jky/ku3-take2.webm, speaker: jky, take: 2, … }         # training-only
  - { url: …/jky/ku3-take3.webm, speaker: jky, take: 3, note: "clipped onset" }
  - { url: …/jky-n/ku3.webm,     speaker: jky-n, synthesis: world-retune, derivedFrom: sha256:… }
```

- **`take`** — integer ≥ 2, optional. Absent means "this speaker's first take at this key". Assigned
  by the merge CLI as max + 1 and **never renumbered**, because it is part of the asset path.
- **`primary: true`** — literal `true`, optional, with no `primary: false` state (the same
  present-and-`true`-only shape as `consentAcknowledged` on the staging proposal type in
  [src/importers/local-recording-types.ts](../../src/importers/local-recording-types.ts)). Within
  one `(pengim, speaker)` group of more than one clip, exactly one clip carries it; a lone clip is
  implicitly primary, so none of the 6,167 existing manifest entries and none of their S3 objects
  change.

**The rule everything else follows from: only primaries leave `data/`.** `dist/`, the web UI, the
mobile app, #274's speaker preference and ADR-0027's `-n` render tier all see one clip per speaker
per syllable, exactly as today; `src/build/enrich.ts` and `src/build/sounds.ts` filter each key to
primaries before anything else runs, which also removes the one place where YAML array order
silently decided playback. Non-primary takes exist for the research tooling that reads the manifest
directly through `manifestClips`. They are not listenable anywhere in the UI; a dev-only "takes"
panel is a later decision, not this one.

The rest falls out:

- **Held-out eval** — queries are a speaker's non-primary takes, references that speaker's
  primaries. That *is* the independent-session split, with no `jky-2` pseudo-speaker.
- **Render tier** — `audio:synthesize` and `merge:resynth` render primaries only, and a `synthesis`
  clip's `derivedFrom` must name a primary recording. The `-n` group at a key therefore always has
  size 1 and the one-job-per-syllable assumption becomes true again. ADR-0027 is amended to say so.
- **Grading** — `audio:grade` pools primaries only, and excludes `synthesis` clips while it is
  there.
- **Storage** — `audioAssetPath(key, speaker, ext, take?)` returns `<speaker>/<pengim>.<ext>` when
  `take` is absent (every existing object) and `<speaker>/<pengim>-take<N>.<ext>` otherwise. Paths
  become immutable: re-recording never overwrites bytes.
- **Merge** — identity is `checksum`. Same checksum already at the key → already merged, no-op,
  exit 0. New checksum and the speaker has no clip at the key → append with no `take`, implicitly
  primary (today's behaviour). New checksum and the speaker already has clips → append as
  `take: N+1`, training-only, splicing `primary: true` into the existing lone clip so the group is
  explicit; `--primary` instead designates the new take and clears the old marker. `--force` is
  retired from `merge:local-recording` and `merge:lingualibre` — there is nothing left for it to
  overwrite. `merge:resynth` keeps its own, because renders do re-publish to the same `-n` path.

Validation replaces `checkDuplicateSpeakers` with four rules: `(speaker, take)` is unique within a
key (absent `take` counts as 1); a `(pengim, speaker)` group of more than one clip has exactly one
`primary: true`; `checksum` is unique within a key; and a `synthesis` clip's `derivedFrom` names a
primary recording at the same key, carrying neither `take` nor `primary` itself. Every state a
human can hand-type — two primaries, none, a deleted primary, a renumbered take — fails
`npm run validate` loudly rather than changing playback silently. That property is worth more than
saving keystrokes on append.

This **refines issue #134's convention rather than reverting it**: one clip per speaker per syllable
is still what every published consumer sees. What changes is that the manifest may hold more than
one, and which one is published becomes an explicit human choice instead of a positional accident.

**Rejected: encode the session in the speaker id (`jky-2`).** What #288's text assumed, and what
`jky-n` already does. Zero schema change, but it is a naming convention with no schema backing
(`jky_2` or `jky-2`?), it fills #274's preference list with pseudo-speakers, and `bestCommonSpeaker`
would treat one person as several when picking a voice for combined playback. **Rejected: implicit
primary = lowest `take`.** Fewer edits on append, but deleting the primary silently promotes another
take; explicit costs one spliced line and makes deletion a forced decision. **Rejected: nesting
`speaker → { primary, takes[] }`.** The honest shape, but it rewrites a 4 MB hand-typed manifest and
every consumer of it. Flat list plus optional fields is what ADR-0027 did, and it worked.
**Rejected: checksum-prefix asset paths** (`ku3-6c361591.webm`) instead of a `take` field. Needs no
field, but it is hostile to anyone reading an S3 listing, and "take 3" is what the CLI output and
the human want to say anyway. **Rejected: a `session` field.** `recorded` already carries the date,
and a session does not discriminate between 8 takes recorded on the same day; `take` + `recorded` +
`note` cover it.

## Consequences

- A contributor can stage and publish as many takes as they record, and ADR-0017's shape is
  untouched — the browser still only stages, a human still merges from the CLI. The default with no
  flags is exactly #288's case: every new take lands training-only and the already-published clip
  stays primary, so a bulk merge can never change what a learner hears.
- Positive: additive and reversible. Both fields are optional and the existing 6,167 clips validate
  and build unchanged on day one; backing the decision out means deleting the non-primary lines and
  their assets, and restoring one `findIndex(c => c.speaker === speaker)`.
- Positive: the re-recording flow loses a step. Because a new take gets its own immutable asset
  path, nothing is overwritten and the manual CloudFront invalidation disappears **for recordings**.
  It remains for ADR-0027's `-n` renders, which re-publish in place.
- Negative: two more `packages/core` schema fields are an exported-type change — a minor version
  bump and a tarball release before the mobile app can read the new manifest (ADR-0024, invariant
  15). The app reads only primaries, so it needs no logic change, but a manifest holding `take`
  entries will not parse against a pinned older core.
- Negative: `audio:grade`'s published per-tone statistics change under it, for two reasons at once —
  non-primary takes are now excluded, and `synthesis` clips are excluded for the first time. The
  `-n` renders have been feeding the very statistics they were tuned toward, so the corpus needs a
  full re-grade and the ADR-0027 targets shift slightly when it happens.
- Negative: "primary" now means two different things a few lines apart. `primary: true` selects
  *within* one speaker's takes in `data/`; `selectPrimaryClip` in `src/build/enrich.ts` selects
  *across* speakers by confidence for single-clip playback. They compose (the second runs over the
  output of the first), but the naming is a trap for the next reader.
- Negative: the manifest grows without the published corpus growing. Held-out eval takes are bytes
  in S3 and lines in the hand-edited manifest ADR-0014 keeps deliberately small, for clips no user
  will ever hear — and nothing prunes them. `audio:verify` fetches and checksums them like any
  other clip, so its runtime grows with the takes too.
- Neutral: `--force` leaving the two recording merges is a small behavioural break for anyone with
  it in a shell history, and it is the point — the flag existed only to authorise data loss that is
  now structurally impossible.
