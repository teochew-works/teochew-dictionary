# ADR-0005: Hand-Editable YAML Is the Product; `dist/` Is Generated

## Status

✅ Accepted

## Context

This project could plausibly have been built around a database — SQLite as the authoritative
store, with an editing tool on top — or around a machine-generated intermediate format that
`src/` reads and writes.

But the thing being built is a *lexicon*, and the work of building it is human: writing a gloss,
choosing a headword, judging whether a Wiktionary candidate is right, deciding a tone. Those are
review-shaped tasks. They want diffs, pull requests, blame, and comments — all of which are
properties of plain text in git, and none of which a binary store has.

Consumers, meanwhile, want the opposite: something indexed and fast, or something streamable.

## Decision

**`data/` is the product.** It is hand-editable YAML — the lexicon in
[data/entries/](../../data/entries/) grouped by semantic field, the phonology tables in
[data/phonology/](../../data/phonology/), the provenance registry in
[data/sources.yaml](../../data/sources.yaml). Everything in `src/` exists to validate that data and
compile it.

**`dist/` is generated and gitignored.** `npm run build` validates, then emits the same content in
whatever shape a consumer needs: `dict.json` (everything, enriched), `dict.ndjson` (one entry per
line, for streaming), `dict.sqlite` (indexed, with FTS5, which
[src/lookup/](../../src/lookup/) searches), and the JSON Schemas of ADR-0004.

Two rules follow and are enforced:

- **Nothing derivable is stored.** IPA, POJ and sandhi (ADR-0001), an entry's `licence` and
  `attributions` (ADR-0008), a sound's `occurrences` count, and `data/wordlists/syllable-inventory.yaml`
  are all computed. The syllable inventory is committed *and* regenerated: `npm run check`
  rebuilds it in memory and asserts it equals the committed file
  ([tests/inventory.test.ts](../../tests/inventory.test.ts)), so a stale copy fails rather than
  rots.
- **Tools that write back to `data/` preserve the bytes they don't change** — see ADR-0018.

## Consequences

- The whole editorial workflow is git's: a lexicon change is a reviewable diff, an argument about a
  gloss happens in a PR, and provenance is `git blame`.
- The dataset is forkable and consumable without this project's tooling. YAML in, three formats out.
- Grouping entries by semantic field (`food.yaml`, `pronouns.yaml`, …) rather than one large file
  keeps diffs local and lets contributors work in parallel without conflicts.
- Negative: YAML has real hazards for this content — a bare `no` or an unquoted string that looks
  numeric. The schemas (ADR-0004) and validator absorb most of it, and blank-line grouping between
  entries is a convention the backfill tooling must not destroy (ADR-0018).
- Negative: scale. At a few hundred entries the files are comfortable; at the 15,000+ candidates
  waiting in `data/staging/wiktionary.yaml` the per-file sizes will need revisiting. The
  semantic-field split is the pressure valve.
- `dist/` being gitignored means every consumer — including `web/`, which copies `dist/dict.json`
  into its own `public/data/` — must build first. `web/`'s `predev`/`prebuild` scripts fail with an
  explicit "run `npm run build` in the repo root first" rather than a missing-file error.
