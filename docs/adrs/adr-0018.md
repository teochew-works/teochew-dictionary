# ADR-0018: Splice YAML Backfills by Byte Offset, Not Parse → Stringify

## Status

✅ Accepted

## Context

Some maintenance work has to write into `data/entries/*.yaml` after the fact: attaching
`tags`/`topics`/`alt_of` from the wiktextract cache (issue #102/#105), filling `level` from an HSK
cognate match (issue #110), and a `retrieved`-date backfill before those. These are not importers —
importers never write to `data/entries/` (ADR-0006) — they are one-off scripts editing
already-approved data.

The obvious implementation is parse the file, mutate the tree, stringify it back.

That destroys the file. These entry files are **hand-typed, not machine-generated**, and `yaml`'s
stringifier does not reproduce them byte-for-byte: it rewraps folded scalars to its own line width,
restyles flow collections (`[one, "1"]` → `[ one, "1" ]`), and drops the blank-line grouping between
entries that makes the files readable. A one-field backfill would arrive as a whole-file diff, and
the actual change would be unreviewable inside it.

## Decision

Backfill scripts **splice new lines directly into the original source string**, at the exact byte
offset a parsed node's `range` reports, rather than round-tripping through the stringifier.

The file is parsed only to *locate* things; every byte the script does not deliberately touch stays
untouched. See [src/importers/entry-tag-matching.ts](../../src/importers/entry-tag-matching.ts),
[src/cli/backfill-wiktionary-tags.ts](../../src/cli/backfill-wiktionary-tags.ts) and
[src/cli/backfill-mandarin-level.ts](../../src/cli/backfill-mandarin-level.ts).

Two conventions travel with it:

- **Dry-run by default**, `--write` to commit. A backfill run is reviewed before it happens, not
  only after.
- **Only fill an absent field.** A backfill never overwrites a value a human wrote.

Where a file is mutated rather than spliced — the audio manifests written by
`merge:lingualibre` and `merge:local-recording` — the same goal is met by `yaml`'s
comment-preserving `parseDocument` + `setIn`, because those files are structurally regular and
carry comments worth keeping. Only `data/entries/*.yaml`, with its hand-tuned formatting, needs
byte-offset splicing.

## Consequences

- **A backfill's diff shows only the lines it added.** That is what makes a several-hundred-entry
  automated edit reviewable at all, and it is what keeps `git blame` on the surrounding lines
  meaningful.
- Hand-tuned formatting — comment blocks, blank-line grouping, deliberate flow-collection style —
  survives automated editing, so ADR-0005's "the YAML is the product" stays true rather than being
  true only until the first script runs.
- Negative: splicing is more fragile than stringifying. It depends on node `range` offsets and on
  the script computing correct indentation for the inserted lines; a subtle bug produces malformed
  YAML rather than a wrong value. Mitigated by `npm run validate` and by dry-run-first.
- Negative: only insertion of absent fields is really supported. Editing or removing an existing
  value in place is not what this technique is good at, and no backfill does it.
- Related, from the same family of concerns: `local-recording-staging.ts` appends into
  `data/staging/teochew-dictionary-audio.yaml` rather than regenerating it, so that a reviewer's
  notes on staged proposals survive (ADR-0017).
