# ADR-0017: Browser Recording Stages a Proposal; Publishing Stays a Human CLI Step

## Status

✅ Accepted

## Context

The Sounds tab (issue #124) lists every syllable attested in the lexicon, and most rows have no
clip. Filling that gap through the import pipeline is useless for a syllable nobody has ever
uploaded to Commons. Issue #128 asked for a **record** control right on the Sounds tab so a
contributor at a microphone can capture one directly — dev-only, since production is a static
GitHub Pages build with no backend to write to.

The literal reading of the issue's acceptance criteria — "after a server restart, entries using
that syllable serve the new recording" — points at the browser's save action re-hosting to a GitHub
Release and writing into `chaozhou.yaml` directly, mirroring what `merge:lingualibre` already does.

**Publishing to a public GitHub Release is a real, externally-visible action.** Today it happens
only when a human deliberately runs a CLI against an already-staged, already-reviewed proposal.
Routing a browser button straight to that effect — no review step, gated only by a client-side
checkbox — lowers the bar for publishing in a way the rest of this pipeline never has.

## Decision

**The record flow stages; it does not publish.** The browser writes bytes to disk and appends a
proposal; publishing stays a separate, human-run merge step — the same shape as the Lingua Libre
flow (ADR-0006).

Recorded explicitly as a consequence rather than an oversight: issue #128's restart-alone
acceptance criterion **is not met**. It also needs `npm run merge:local-recording`.

Three supporting choices:

- **A new proposal shape, not a repurposed one.** `AudioClipProposal`
  ([src/importers/audio-types.ts](../../src/importers/audio-types.ts)) is Commons-shaped
  (`commonsTitle`, `commonsUrl`, licence recovered from `imageinfo`) with no room for a clip that
  was never fetched from anywhere. `LocalRecordingProposal`
  ([local-recording-types.ts](../../src/importers/local-recording-types.ts)) is parallel to it,
  staged to `data/staging/teochew-dictionary-audio.yaml`. Its writer **appends** into the existing
  document via `parseDocument` + mutate, rather than regenerating the file the way a batch importer
  does, so a reviewer's own notes on already-staged entries survive a later browser-triggered save.
- **Recorded bytes are committed, not gitignored.** The project's gitignored scratch convention
  (`.cache/`, ADR-0013) is for anything refetchable — and a spoken recording is not refetchable.
  `data/staging/recordings/` holds the raw bytes beside the proposal that references them, so a
  reviewer on any machine can listen to what they are being asked to merge via a normal PR diff,
  and nothing depends on the contributor's own machine still having the file.
- **Merge reuses `rehostClip`'s shape, not its code path.** A local recording has no URL to fetch,
  so the tmp-file / `gh release upload` / sha256 logic was factored out of
  [lingualibre-rehost.ts](../../src/importers/lingualibre-rehost.ts) into a shared
  `uploadBytesToRelease` that both the fetch-from-Commons and read-from-disk paths call.
  [local-recording-merge.ts](../../src/importers/local-recording-merge.ts) otherwise mirrors
  `mergeLinguaLibreClip`: refuses to overwrite without `--force`, builds a clip with
  `confidence: 'high'` (a first-party recording, not scraped metadata of uncertain fit), and writes
  back with the same comment-preserving mutation. On success it deletes the staged proposal and
  local file — once the bytes live on a Release, the staged copy is only a second, driftable copy.

## Consequences

- The staging boundary (ADR-0006) holds for a UI, not just for importers. Nothing in this project
  publishes without a human running a command.
- A recording is reviewable *by listening to it* in the PR, which no URL-and-checksum manifest
  alone allows.
- Negative: capturing a clip is a two-step process, and the second step is easy to forget. The
  issue's own acceptance criterion is the first casualty, which is why it is written down here.
- Negative: committing raw audio to `data/staging/recordings/` puts binary bytes in git history —
  the exact thing ADR-0014 avoids. Bounded deliberately: the files are transient, deleted on merge,
  and the alternative is losing an unrepeatable recording.
- The record flow is dev-only middleware ([web/vite-plugins/](../../web/vite-plugins/)); production
  builds have no such endpoint, so the static-hosting assumption of ADR-0019 is unaffected.
