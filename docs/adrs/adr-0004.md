# ADR-0004: Zod Schemas as the Source of Truth for Types and JSON Schema

## Status

✅ Accepted

## Context

The dataset is hand-edited YAML, so it needs three things that are easy to let drift apart:

1. **Runtime validation** — a hand-typed file must be checked before anything downstream trusts it.
2. **TypeScript types** — every tool in `src/` operates on parsed entries.
3. **A published JSON Schema** — so an editor can offer completion and inline errors while someone
   types an entry, and so an external consumer can validate `data/entries/*.yaml` without running
   this project's code.

Maintaining these as three separate artifacts — a validator, an interface, a `.json` schema file —
guarantees they diverge, and the divergence is silent: the types still compile, the validator still
runs, and only the schema quietly stops describing the data.

## Decision

We will define each shape **once, as a Zod schema**, and derive both the TypeScript types and the
published JSON Schemas from it.

*Amended 2026-09-05 by [ADR-0024](adr-0024.md):* the entry and phonology schemas moved unchanged
into `packages/core/` so the mobile app shares them; only the root-tooling schemas and the emitter
remain in `src/schema/`. The "define once, derive the rest" decision is unchanged — what moved is
the directory.

- [packages/core/src/schema/entry.ts](../../packages/core/src/schema/entry.ts) and
  [phonology.ts](../../packages/core/src/schema/phonology.ts) (shared with `web/` and the mobile
  app) and [src/schema/inventory.ts](../../src/schema/inventory.ts) (root tooling only) hold the
  schemas; types are inferred from them.
- [src/schema/emit.ts](../../src/schema/emit.ts) emits the JSON Schemas via `z.toJSONSchema`,
  targeting draft-07. `npm run schema` writes them alone; `npm run build` writes them alongside the
  data artifacts.
- Every hand-edited file family gets its own schema (issue #39, 2026-08-16, resolved in
  [REVIEW.md § 15](../../data/phonology/REVIEW.md)): `schema.json` for entries, plus
  `pengim-schema.json`, `poj-schema.json`, `variety-schema.json`, `sandhi-schema.json`,
  `external-chart-schema.json`, `audio-schema.json` and `syllable-inventory-schema.json`. The scope
  rule is *hand-edited files get a schema* — the phonology tables are as hand-typed as the entries
  are, so restricting emission to `schema.json` would have left the harder files unassisted.

Two deliberate details in the emission:

- `io: 'input'` — the JSON Schema describes the **pre-transform** shape (a checksum's regex, not
  its lowercased output), because a Zod transform has no JSON Schema representation and the schema
  exists to validate what someone *types*.
- Variety ids are injected into the generated artifact rather than declared as a `z.enum`. The
  legal set is filesystem-derived (ADR-0002), so encoding it statically in the Zod schema would
  couple schema definition to directory contents at module-load time. `entryFileJsonSchema` patches
  the enum into the emitted schema only.

## Consequences

- One edit changes validation, types and the published schema together; they cannot drift.
- Contributors get editor completion and inline errors while typing an entry or a phonology table,
  which is the highest-leverage place to catch a mistake — before `npm run validate` runs.
- `dist/*-schema.json` is a real interoperability artifact: an external consumer can validate the
  data without running this project's TypeScript.
- Negative: the JSON Schemas are generated output and must be regenerated when a schema changes;
  `npm run check` covers this via the build and [tests/schema.test.ts](../../tests/schema.test.ts).
- Negative: JSON Schema cannot express everything the Zod schemas and validator do. The cross-file
  rules — ids unique, sources resolve, tone/coda agreement, derivation succeeds — live only in
  `npm run validate` (see [src/validate/index.ts](../../src/validate/index.ts)), so a file that
  passes its JSON Schema in an editor can still fail validation. That split is inherent, not a
  defect of this choice.
- The injected-enum workaround is a small, documented seam between "the schema" and "the emitted
  schema" that a future change to variety handling has to keep in mind.
