# ADR-0012: Keep Network Access Out of `npm run check`

## Status

✅ Accepted

## Context

Several of this project's operations genuinely need the network: importing from Wiktionary or
Commons, refreshing a cached external phonology chart, and verifying that every declared audio clip
still exists at its URL with the right checksum. Audio in particular is hosted outside the repo
(ADR-0014), so its bytes are only checkable over HTTP.

It would be natural to fold those into the standard check — a validator that verified checksums
would catch a real class of error.

It would also make the standard check slow, flaky, dependent on third-party availability and rate
limits, and unusable in CI or offline. Worse, it would make the *failure* ambiguous: a red build
would no longer distinguish "the data is wrong" from "Commons is having a bad afternoon".

## Decision

`npm run check` — `typecheck && test && validate` — is **fast, offline and CI-safe**. Nothing in it
touches the network.

Network-touching work is confined to explicitly-invoked commands, each of which is a deliberate act:

| Command | What it reaches |
|---|---|
| `npm run import -- <source>` | Wiktionary / Commons, into `data/staging/` |
| `npm run cache:wiktionary` | Wiktionary wikitext, into `.cache/` |
| `npm run xref -- <source>` | an external phonology chart, into `data/phonology/external/` |
| `npm run audio:verify` | every declared clip's bytes, to confirm its checksum |

`checkAudio` ([src/validate/index.ts](../../src/validate/index.ts)) therefore checks only that clip
metadata is **internally consistent** — legal syllable, resolvable licence, well-formed pinned
Release URL. It deliberately does not fetch `clip.url` or verify `checksum` against real bytes;
that is `npm run audio:verify`'s job (see also [REVIEW.md § 12](../../data/phonology/REVIEW.md),
which records the same boundary when the URL field was introduced).

CI ([.github/workflows/ci.yml](../../.github/workflows/ci.yml)) runs `npm run check` at the root and
`npm run check` plus a build in `web/`, and nothing else.

## Consequences

- CI is deterministic. A red build means the repository is wrong, not that a third party was slow.
- Contributors can validate the dataset on a plane, and a fast local `check` stays worth running
  before every commit.
- Rate-limit and User-Agent handling is confined to the importers, where it belongs — see
  `IMPORTER_USER_AGENT` and `RetryOptions` in
  [src/importers/types.ts](../../src/importers/types.ts), including the per-attempt (not
  whole-sequence) timeout and the capped `retry-after` honouring added in issue #125.
- Negative: **the gap is real and unmonitored.** Nothing routinely detects an audio Release asset
  that has been deleted or replaced. `audio:verify` exists but runs only when someone runs it. A
  scheduled workflow would be the natural mitigation and is not in place.
- Negative: a cached external chart can silently go stale; `npm run xref` refreshes it only on
  demand.
