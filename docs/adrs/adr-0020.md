# ADR-0020: A Hand-Rolled SM-2 Scheduler over IndexedDB

## Status

✅ Accepted

## Context

The flashcard trainer needs spaced repetition, which means a scheduling algorithm and somewhere to
keep per-card state. ADR-0019 rules out a server, so state is per-browser.

Off-the-shelf SRS libraries exist. They also bring their own storage assumptions, their own card
model, and a dependency in a project whose stated approach is minimal dependencies — for an
algorithm that is, in its SM-2 form, a few dozen lines of arithmetic.

For storage, `localStorage` is simplest but is synchronous, string-only, and small. IndexedDB is
the right shape for a growing keyed store, with an awkward API.

## Decision

*Amended 2026-09-05 by [ADR-0024](adr-0024.md):* the scheduler and the deck pipeline moved
unchanged into `packages/core/` (`@teochew/core`) so the mobile app runs the same maths; the
IndexedDB and localStorage persistence, and the queue hook, stay in `web/`. Nothing below about
*how* scheduling works changed — only where the pure part lives.

- **A hand-rolled SM-2-style scheduler**, no dependency
  ([packages/core/src/srs/scheduler.ts](../../packages/core/src/srs/scheduler.ts)), with a
  three-button grading UI (Again / Good / Easy).
- **Persisted via [`idb`](https://github.com/jakearchibald/idb)** — a thin promise wrapper, not an
  ORM — to an IndexedDB database `teochew-flashcards`, object store `cards`, keyed by entry id
  ([web/src/srs/db.ts](../../web/src/srs/db.ts)).
- **Deck membership, the table, and saved groups persist to `localStorage`** under
  `teochew-dictionary:decks/v1` ([web/src/decks/storage.ts](../../web/src/decks/storage.ts)) —
  small, bounded, synchronous-friendly config. Review scheduling stays in IndexedDB. The split is
  by data shape, not by convenience.
- **The drawn card has continuity** ([web/src/srs/useSrsQueue.ts](../../web/src/srs/useSrsQueue.ts)).
  A review queue is kept per *table* — the set of decks in play, order-insensitive — so taking a
  deck off the table and putting it back returns to the card the first table was showing, with its
  own progress. Within a table the queue changes only when something in it becomes ineligible: it
  is pruned of cards that left the pool and topped up only when the pool grows. Renaming a deck,
  filing a card, reordering the library, or changing a filter the card still passes all leave it
  alone. Rebuilding on every pool change instead reshuffles — which is how an unrelated deck rename
  used to deal a different card.
- New-card ties are **shuffled**, not sorted by id (issue #157 follow-up), so the queue is not
  alphabetical by accident.

## Consequences

- The scheduling math is in this repository, readable and unit-tested
  ([scheduler.test.ts](../../packages/core/src/srs/scheduler.test.ts)), and tunable for a
  dictionary's needs without fighting a library's model.
- No dependency for the core algorithm; the one storage dependency is a wrapper thin enough to
  replace.
- Card continuity is a correctness property, and treating it as one caught a real bug class: the
  naive "recompute the queue whenever the pool changes" implementation made unrelated edits
  reshuffle the session.
- Negative: **progress is per-browser and per-device.** Clearing site data loses it, and there is
  no sync — a direct consequence of ADR-0019's non-goals, stated so it does not read as an omission.
- Negative: **IndexedDB persistence is not covered by the test suite** — `jsdom` does not implement
  it. Verifying it is a documented manual step (grade a few cards, reload, confirm they do not
  reappear as new). The scheduling math and the queue logic *are* tested; only the storage layer is
  not.
- Negative: SM-2 is a 1980s algorithm, superseded in the SRS world by FSRS and similar. Chosen for
  being small enough to own outright; revisiting it means rewriting one tested file.
