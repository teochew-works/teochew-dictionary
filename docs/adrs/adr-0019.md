# ADR-0019: A Static, Backend-Free Web UI as an Independent npm Project

## Status

✅ Accepted

## Context

The dictionary needed a way to be used by people who are not going to run
`npm run lookup` from a terminal (issue #55): a browsable dictionary with search, and a flashcard
trainer.

Anything with a server changes the project's nature. It needs hosting, a deployment story,
uptime, and an operator — for a personal-scale lexicon project maintained by volunteers, that is a
liability out of proportion to the feature. It would also put a service between the data and its
consumers, when the whole point of ADR-0005 is that the data is the product.

The second question was where the frontend lives. Folding React, Vite and a browser test
environment into the root `package.json` would put the CLI tooling's dependency tree and the app's
in the same place, and make every root `npm run check` carry the app's build.

## Decision

`web/` is a **static, backend-free frontend** and an **independent npm project**.

- Vite + React + TypeScript, **no router** — Dictionary, Flashcards, Sounds and Settings are in-app
  views, not routes, and the entry detail is a master-detail pane within its view. Tab navigation is
  still real links, so Cmd/Ctrl+click opens a new tab (issue #156).
- **Plain CSS, no UI framework**, matching the root project's minimal-dependency approach.
- Its own `package.json`, `tsconfig`, test suite and `npm run check`. CI runs each project's
  checks separately ([.github/workflows/ci.yml](../../.github/workflows/ci.yml)). *Since
  2026-09-02 there are three:* the logic `web/` shares with the mobile app lives in a third
  independent project, `packages/core/`, that `web/` depends on the ordinary npm way
  ([ADR-0024](adr-0024.md)) — the same "separate trees" reasoning as this ADR, applied once more.
- It **consumes** `dist/dict.json`, `dist/sounds.json` and `dist/syllable-chart.json` rather than
  duplicating any data-loading logic. `scripts/sync-data.mjs` copies them into `web/public/data/`
  via `predev`/`prebuild`; they are **fetched at runtime as static assets, not bundled as a JS
  import**, so the dataset can grow without bloating the JS bundle. The scripts only *copy* — if
  the build output is missing they fail with "run `npm run build` in the repo root first".
- Anything genuinely derivable is precomputed at build time in `src/` rather than in the browser:
  `search_keys` ([src/build/enrich.ts](../../src/build/enrich.ts)), the sound inventory with its
  occurrence counts ([src/build/sounds.ts](../../src/build/sounds.ts)), and the syllable chart
  ([src/build/syllable-chart.ts](../../src/build/syllable-chart.ts)) — reusing the same attestation
  and IPA-derivation logic the CLI uses, rather than reimplementing Peng'im parsing in TypeScript
  for the browser.
- Deployed to GitHub Pages by [.github/workflows/deploy.yml](../../.github/workflows/deploy.yml) on
  every push to `main` touching `web/`, `data/` or `src/`.

Explicit v1 non-goals: user accounts or cross-device sync, and offline/PWA support.

**The PWA half of that has since been reversed** by [ADR-0023](adr-0023.md) (issue #194): the app
now ships installable, with a Workbox-generated service worker precaching the shell. The driver was
not offline access but storage durability — Safari's ITP sweeps script-writable storage after seven
days without a visit, which would take the SRS history with it (ADR-0020), and a home-screen
install is exempt. Backend-free is unchanged; cross-device sync remains a non-goal.

## Consequences

- **Zero hosting cost and zero operational burden.** A static bundle deploys to any static host;
  there is no service to keep up.
- The frontend cannot diverge from the data model by reimplementing it — it renders what the build
  already derived, so a phonology fix (ADR-0001) reaches the web UI without a second implementation
  to update.
- The two npm projects can move independently; a frontend dependency bump does not touch the CLI's
  tree.
- Negative: **no backend means no shared state.** Flashcard progress is per-browser (ADR-0020), and
  the cross-device-sync non-goal is a consequence of this decision rather than an independent
  scoping choice. It also makes browser storage eviction an existential risk rather than an
  inconvenience, which is what [ADR-0023](adr-0023.md) later answers.
- Negative: two `package.json` files, two lockfiles, two `npm ci` steps in CI, and a build-order
  dependency contributors hit the first time they run `npm run dev` without having built.
- Negative: served from a project subpath, so `vite.config.ts` sets `base: '/teochew-dictionary/'`
  only for the Pages build via a `GH_PAGES` env var. **If a custom domain is ever attached, `base`
  must revert to `'/'` and a `CNAME` added, or the deployed site serves broken asset URLs.**
- Negative: the whole dataset is fetched client-side. Fine at the current size; a five-figure
  lexicon (ADR-0011) will eventually need chunking or an index.
