# ADR-0028: Load-Time Reading Patches for Upstream-Sourced Errors

## Status

✅ Accepted

## Context

Issue #282 (2026-09-13) found six Peng'im typos and several reversed spellings copied verbatim into
`data/entries/*.yaml` from Wiktionary — rimes that exist in no published scheme, faithfully imported
because Wiktionary itself has them wrong — plus roughly 242 readings mistagged with the default
`variety: chaozhou` when they are actually a different locality's form (ADR-0002's variety-mixing
problem).

The issue's own recommendation for the six typos is the obvious one: correct `pengim` in
`data/entries/`, keep `sources: [wiktionary]` intact for licence provenance (ADR-0008), and justify
the change with a `note`. That is exactly what ADR-0018's byte-offset-splice backfills are built
for.

That recommendation assumes the correction can simply replace what's on disk and stay there. It
can't here: these entries are a faithful mirror of the Wiktionary import (ADR-0006 — importers
propose into `data/staging/`, a human merges into `data/entries/`, but the merged content is still,
by design, the source's own text). Hand-editing the merged `pengim` value directly would make
`data/entries/` diverge from what `sources: [wiktionary]` actually says — silently misrepresenting
provenance for exactly the reason ADR-0006 and ADR-0008 both exist to prevent — and a future refresh
of the Wiktionary import has no way to know a given value was deliberately overridden rather than
simply stale, so it re-proposes the same error every time. The fix needs to be correct *and* survive
indefinitely alongside byte-identical source text, which byte-offset splicing (ADR-0018) doesn't
offer: that mechanism edits `data/entries/` itself.

## Decision

We will correct known-wrong `pengim`/`variety` values **at load time**, in memory, never by editing
`data/entries/` or `data/staging/`.

- `data/patches/*.yaml` holds a flat list of patch records (schema:
  [src/schema/patches.ts](../../src/schema/patches.ts)), each identifying a reading by
  `entry` id + its exact on-disk `pengim` string (stable and human-legible in review, unlike a
  reading index that can shift), the field(s) to `set` (`pengim` and/or `variety`), a `reason`
  citing the evidence, and a `confidence` (ADR-0003's vocabulary).
- [src/data/load.ts](../../src/data/load.ts)'s `readEntryFiles()` applies every patch
  ([src/data/patches.ts](../../src/data/patches.ts)) immediately after the raw YAML read and before
  any consumer sees it — the one seam `loadEntries()` (build, the syllable inventory) reads through.
  `src/validate/index.ts` reads the *unpatched* raw instead, specifically so it can also check that
  every patch still applies.
- A patch that matches zero or more than one reading is never silently dropped: it's left unapplied
  and reported as a validation **error**, so a stale patch (the upstream source was fixed, or the
  entry text changed underneath it) fails `npm run check` loudly rather than quietly no-op'ing
  forever.
- Applying a patch injects a `note` on the affected reading (unless one is already present),
  documenting the correction and citing the patch id — the fix is visible in `dist/dict.json` and
  the web UI, not just baked invisibly into derived IPA/POJ.

This is a new mechanism, not an extension of ADR-0018: it exists specifically for data that must
stay byte-identical to its import source, which byte-offset splicing was never meant to serve. Both
now cover a correction, for different reasons — ADR-0018 when the on-disk value should simply become
right, this ADR when the on-disk value must keep faithfully recording what the source said.

## Consequences

- `data/entries/*.yaml` never diverges from `sources: [wiktionary]`'s actual text, so provenance
  stays honest and a re-run of `npm run import -- wiktionary` can't produce a misleading diff against
  a hand-edited value.
- A correction is invisible in `git diff data/entries/` — it only shows up in `data/patches/` and in
  the derived `dist/` output. Anyone auditing "what changed in the data" has to know to look in both
  places; `git log data/patches/` is the trail for this class of edit.
- `data/patches/` is itself a small, hand-reviewed, checked-in file — visible and diffable the same
  way the rest of `data/` is, in keeping with ADR-0005's "hand-editable is the product."
- The mechanism scales to Finding 3's ~242 variety mistags (each just another patch with `set.variety`
  instead of `set.pengim`) once that per-reading list is regenerated — a separate, later effort; only
  the six Finding-1 typos and two illustrative Finding-2 reversals are patched as of this ADR.
- Negative: a patch is one more place a reading's true value can hide. Anyone reading
  `data/entries/` alone sees the *wrong* value; understanding the actual dataset requires knowing
  `data/patches/` exists. Mitigated by the injected `note` surfacing the correction downstream, and
  by the loud validation failure if a patch ever goes stale.
- Negative: this is explicitly not a general-purpose backfill mechanism. It exists for values that
  are correct-in-spirit to override but must never be edited in place; ADR-0018 remains the right
  tool for additive fields that are fine to land as ordinary edited bytes.
